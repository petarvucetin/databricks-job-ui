# Three environments (dev / stg / prod) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** One laptop console that switches between the dev, stg and prod workspaces, plus one deployed app per workspace that shows its env label.

**Architecture:** The server builds one `WorkspaceEnv` per configured env, lazily. Each is the existing provider stack (`selectRunSource`) fed a per-env copy of the env vars, with that env's CLI profile and warehouse, plus its own capture store and memos. An `EnvRouter` picks the `WorkspaceEnv` from `?env=` on every request. The client adds `env` to every API URL. A switch is a full page load to `?env=<new>&tab=<tab>`. Deployed apps get `JOBS_CONSOLE_ENV` from their bundle target's `config.env`.

**Tech Stack:** Node 22, Express via AppKit 0.57, `@databricks/sdk-experimental` `WorkspaceClient`/`Config`, React 19, vitest (+ jsdom, @testing-library/react), Databricks CLI 1.5 bundles, PowerShell 5.1+ scripts.

**Spec:** `docs/superpowers/specs/2026-10-20-multi-env-design.md` (decisions E1–E18). Mockup: `docs/design/mockups/env-switch.html`, variant A.

All paths below are relative to `jobs-console/` unless they start with `docs/`.

## Global Constraints

- Env names are exactly `dev`, `stg`, `prod`, always ordered dev → stg → prod (E1).
- `run-local.ps1 -Profile x`, `npm run dev`, mock, replay, the `default` target and the Marketplace installer behave exactly as before when `JOBS_CONSOLE_ENVS` / `JOBS_CONSOLE_ENV` are unset (spec Goal 4).
- No client workspace URL or warehouse id is committed (Goal 5).
- Colors only from `client/src/styles/tokens.css`: stg `--amber`, prod `--red`, dev none. Top edge is 3 px (E7).
- Title copy: `DEV · Jobs console`, `STG · Jobs console`, `PROD · Jobs console` (E8).
- Error copy for a failed env names the fix: `databricks auth login --profile <profile>` (E10).
- The repo's files are CRLF: edit existing files with the Edit tool, never `sed -i`.
- Commit with a pathspec (`git commit -m ... -- <paths>`); parallel agents share the index.
- Every UI/server change ships to the laptop: `npm run package`, commit `deploy/`, push (Task 10).

## Review Focus

1. **A response from the old env landing after a switch.** The switch must be a real navigation (`window.location.assign`), not a state change. Task 7 tests that clicking an env calls `location.assign` with the new URL and renders nothing from the old one.
2. **Tab changes, the compare page and "open compare in new tab" dropping `?env=`**, which silently moves the user to the first env (dev) while they think they are in prod. Task 6 tests each rewrite site.
3. **One env's login expired.** The other envs must keep working, and the failing env says which `databricks auth login --profile` to run. Task 4 tests a provider whose client throws for one env only.
4. **`DATABRICKS_HOST` / `DATABRICKS_CONFIG_PROFILE` left in `.env` or the shell while `JOBS_CONSOLE_ENVS` is set.** Every env would then silently read the same workspace. Task 3 tests that per-env records clear them, and Task 2 tests that the profile is passed explicitly to the SDK.
5. **Two envs sharing a cache.** Today every key is `'dev'`/`'app'` locally. Task 3 tests that two `WorkspaceEnv`s on the mock and live paths hold distinct provider instances and that data listed through one never appears in the other.
